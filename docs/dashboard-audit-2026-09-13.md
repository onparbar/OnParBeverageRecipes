# On Par dashboard audit — September 13, 2026

The dashboard has useful operational depth and a recognizable, cohesive visual identity. Keep the cream background, dark green accents, serif titles, simple navigation, and the focus on real beverage work. The next improvement should be to make the existing features agree with each other and shorten the path from a finding to its next action.

This was an audit, not an implementation or deployment. I inspected the live owner dashboard at [onparbev.com](https://onparbev.com), including Home, Keg Levels, Inventory, Weekly Plan, Weekly Snapshots, Weekly Usage, Tap Pricing, Ingredient & Keg Costs, Recipes, Add Product, Performance, and Print. I inspected Staff View's overview and receiving page using the existing administrator session. Three parallel source reviews covered workflows, feature correctness, and efficiency. Existing working-tree changes were preserved.

I did not submit orders, change counts or prices, publish products, mark prep/receiving/printing complete, or repair taps. Normal navigation can trigger the app's existing refresh and synchronization. Findings labeled **source/reproduction** describe the current local code; they do not establish that a live transaction has already produced bad business data or that every local change is deployed. Speech recognition, external checkout, live PMB writes, and a real employee login were not exercised. A temporary 390px viewport showed a usable staff layout, and the owner keg table's measured width fit its container; the owner screenshot capture was inconsistent, so physical phone usability remains unverified. The viewport was restored.

The full automated suite completed with **919 tests: 916 passed, 3 failed**. Lint passed. The failures concern one health-check request-count assertion and two tap-history schema/label assertions. These appear to be source/test contract mismatches and need resolving; they are not proof that those live features are broken. Initial sandbox-only loopback failures disappeared when the local mock-server tests were rerun with networking allowed. Additional in-memory reproductions exposed accounting cases not covered by the passing workflow tests.

Some earlier audit findings have been addressed. Header search and its keyboard shortcut are wired in current source; top-N and profit queries now work in the live walkthrough. Pricing's “Need review” is actionable, Performance includes All walls and week coverage, and weekly count/snapshot checks are stronger. Those should not be treated as unresolved September 6 findings.

The following fixes deserve priority, in order of their effect on stock and decisions:

1. **A recount can allow a receipt to add stock twice — source/reproduction, high priority.** Start with 10 bottles, receive 5, physically recount 15, then rebuild the same receipt contribution: the result becomes 20. A manual count clears the prior contribution record, while receiving recomputes received lines for the vendor. Preserve receipt identity across recounts and reconcile events relative to the count's effective time. Acceptance: receipt retries and edits to another line from that vendor must leave the recounted stock correct. Evidence: [count handling](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/lib/inventory-store.mjs:590), [batch counts](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/lib/inventory-store.mjs:619), [receipt contributions](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/lib/inventory-contributions.mjs:382).

2. **Reopening prep after a shortage can create stock — source/reproduction, high priority.** Start with 1 bottle; complete prep requiring 2; the displayed quantity clamps to 0; reopen the prep and it becomes 2, instead of the original 1. Record the shortage or the actual reversible adjustment so undo restores the exact prior balance. Evidence: [adjustment calculation](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/lib/inventory-store.mjs:673).

3. **Receiving beer does not fully update backup keg stock — source, high priority.** Unmapped beer-keg receipt lines are skipped by cabinet contributions, while keg forecasting uses separate backup/On Deck quantities. A received checklist is therefore not sufficient evidence that keg stock increased. At receiving, allocate to current-product backup, On Deck, or an unresolved destination and apply the quantity once. Acceptance: receiving one keg changes the appropriate stock pool and next recommendation without requiring a second manual count. Evidence: [skipped receipt lines](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/lib/inventory-contributions.mjs:388), [forecast stock inputs](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/lib/par-agent.mjs:705).

4. **Some inventory exceptions disappear behind successful prep saves — source.** The API returns reviewRequired/reviewItems, but owner and staff clients primarily consume warning. Some unmapped recipe ingredients are also silently skipped. Distinguish intentional exclusions from unresolved mappings and show “Prep saved · inventory needs review,” linked to the affected items. Evidence: [API response](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/app/api/staff-prep-plan/route.js:198), [staff client](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/staff-dashboard.js:1026), [owner client](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:5970), [ingredient mapping](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/lib/inventory-contributions.mjs:219).

5. **An individually cleared count can still count as a current zero — source/reproduction.** A blank edit deletes the number but records a current count timestamp. Readiness uses that timestamp, and the input can render the missing value as zero. Clearing all counts now handles timestamps properly; the remaining bug is narrower. Blank should mean uncounted; an entered 0 should mean counted and empty. Evidence: [blank edit](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/lib/inventory-store.mjs:586), [readiness](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/inventory-weekly-counts.mjs:12), [input display](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:15725).

6. **Search can re-admit data the shared validator rejected — source/reproduction.** The search fallback turns null into zero, accepts explicitly unusable numeric entries, and can interpret a sales-source number as poured ounces. The normal questions tested live work, but incomplete or incompatible records can still produce misleading results. Remove this fallback and use the same validity/coverage rules as other views. Evidence: [search conversion](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:3614), [canonical validator](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/weekly-usage-performance.mjs:66).

7. **All-time history can mix incompatible intervals — source/reproduction.** Existing history includes a long August-to-November interval and overlapping November intervals. A bounded reproduction admitted those five entries as five weeks without reporting conflicts. This threatens all-time comparisons; it does not establish that recent six-week results are wrong. Validate full date ranges, identify overlaps, and flag questionable records for review while preserving the original history. Evidence: [period parser](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/weekly-usage-seller-rankings.mjs:120), [history import](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:19306), [CSV history](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/data/weekly-usage-history.csv:5).

8. **“Save recipe draft” does not create a separate draft — source.** A name-only recipe enters the recipe collection without a draft status; missing costs can become zero. Use Draft → Ready → Current, with incomplete items excluded from the staff current library. Evidence: [recipe save](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:16351), [cost fallback](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:18515).

9. **Beer setup has an avoidable lookup dependency — live fields/source validation.** ABV is not manually exposed, while saving requires positive lookup-derived ABV, an image, and a description. Allow reviewed manual metadata and a branded image fallback; handle 0.0% products if they are in scope. Evidence: [validation](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:16413), [hidden field](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/app/page.jsx:568).

10. **Small interaction gaps create extra work — live/source.** Search's usage links open the whole table instead of the named item; Performance products are plain text; ordinary Enter is intercepted in textareas. Link to the exact item and restrict spreadsheet-style Enter navigation to count grids. Evidence: [search destination](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:3606), [performance rows](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:7127), [Enter handling](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:12039).

The visual change I would make first is to shrink the owner header and the “This week” banner. In the desktop capture, branding/navigation occupied roughly 270 pixels and the week banner another 140, pushing much of the useful work below the initial view. Keep the branding, but use a compact masthead and a dated weekly heading. Use the existing green for the primary action, neutral cards for information, and warning color for exceptions. Add visible words where meaning depends on a color or symbol.

There are also several technical efficiency gains that do not require a redesign:

- **Make navigation usable immediately.** Startup currently awaits shared and ancillary reads before binding events. Load independent data concurrently, display cached/available sections early, give requests time limits, and provide a section-specific retry state. Evidence: [startup](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:1294), [blocking reads](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:1343).
- **Render only what changed.** The main render function rebuilds many hidden sections. Use the existing render coordinator for affected panels/rows and defer unopened panels. This is a source-based opportunity, not a measured browser speed claim. Evidence: [full render](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:3476).
- **Cache code by release.** The roughly 881 KB dashboard script uses a fresh timestamp URL on each mount plus no-store headers. Version/hash static code and load secondary features on demand while continuing to refresh operational data. Evidence: [script loading](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/app/page.jsx:89), [headers](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/next.config.mjs:19).
- **Standardize saves and recovery.** Revision-aware outboxes, conflict handling, PMB request deduplication, batched rendering, and hidden-tab refresh suppression are good foundations. Route remaining direct localStorage saves through the same error/recovery handling. Evidence: [outbox](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/operational-outbox.mjs:30), [refresh coordination](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:1454), [save path](/Users/samanthawatkins/Desktop/OnParBeverageRecipes-main/public/dashboard.js:20319).
- **Remember context.** Preserve the chosen wall, period, section, and product in user preferences or URLs as appropriate, so returning from Staff View or reloading does not require setting up the same view again.

For the next work cycle, fix stock reconciliation and the missing/invalid-data cases first; resolve the three failing assertions and add tests for the reproduced edge cases. Then implement the compact header/attention area and exact-product links. The shared drawer and focused count/receive modes can follow. That order preserves the useful features while improving trust, simplicity, and day-to-day speed.
